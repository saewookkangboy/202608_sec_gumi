# Day 3 — MCP 연동 (PRD 기반 가상 MCP)

> 레포 경로: `mx-agentic-ai-day3-mcp-tools/README.md`
>
> ⚠️ 참고: 예전 Day 3에서는 실제로 동작하는 Node MCP 서버(`npm test && npm run smoke`)를 썼어요. 이번 버전은 개발 경험이 많지 않은 교육생도 따라올 수 있도록 **계약 설계와 가상 응답** 중심으로 단순하게 바꿨어요. 기존 서버 코드(`src/` 등)가 있다면 지우지 말고, [선택] 단계에서 그대로 이어서 확장해도 됩니다.

**교육 질문**: PRD Canvas 5의 AI 역할을 도구로 쪼갠다면, 그 도구가 실제로 존재한다고 가정할 때 계약은 어떤 모양이어야 할까요?

---

## 이론

**MCP(Model Context Protocol)란**
AI가 외부 도구나 데이터에 표준화된 방식으로 접근할 수 있게 해 주는 프로토콜이에요. 핵심은 도구를 "계약(contract)"으로 먼저 정의하는 것입니다. 입력 스키마, 출력 스키마, 그리고 오류 상황까지요.

**왜 "가상" MCP인가**
계약과 모의 응답(mock)으로 설계부터 검증해 보는 거예요. 계약이 정확하면 나중에 실제 구현으로 그대로 바꿔 끼울 수 있거든요. Day 3의 목표는 "동작하는 코드"가 아니라 "정확한 설계"입니다.

**읽기 도구 vs 쓰기 도구**
- 읽기 도구: 조회만 하니까 자유롭게 실행해도 돼요
- 쓰기 도구: 보고서 저장, 발주, 알림 발송처럼 흔적을 남기는 도구라 승인 토큰이 필요해요

이 구분이 Day 4의 HITL 게이트로 그대로 이어집니다.

## 예제 (오늘 쓸 프롬프트 — 순서대로)

**1) 확산 — 도구 후보**
```
../mx-agentic-ai-day1-prd/docs/prd.md의 AI 역할을 실행하려면
어떤 외부 데이터·시스템에 접근해야 하나요? 읽기만 하면 되는 것과,
뭔가 쓰거나 실행해야 하는 것을 구분해서 나한테 물어봐 주세요.
```

**2) 수렴 — 계약 설계**
```
이 중 하나를 골라서, 입력/출력/오류 상황을
JSON Schema로 설계하도록 나한테 물어봐 주세요.
출력엔 반드시 근거 ID 필드가 있어야 해요.
mcp/[도구명]/contract.json으로 저장해 주세요.
```

**3) 가상 실행**
```
실제 서버 코드 없이, 이 도구가 호출됐다고 가정하고
Claude Code 안에서 가짜 응답(mock)을 만들어서
mcp/[도구명]/mock-response.json에 저장해 주세요.
그 응답이 계약과 일치하는지, 근거 ID가 빠짐없는지
나한테 검토시켜 주세요.
```

**4) 승인 규칙**
```
이 도구 중에 사람 승인 없이 실행되면 위험한 게 있나요?
왜 위험한지 나한테 물어봐서 승인 토큰이 필요한 도구를
approval-rule.md에 표시해 주세요.
```

**5) [선택] 실제 구현 — SW 개발 가능 팀만**
```
이 계약대로 최소 동작하는 서버를 실제로 만들어보고 싶다면
뭐부터 시작해야 할지 물어봐 주세요. 이 폴더에 기존 Node 서버
코드가 있는지 먼저 확인하고, 있다면 그걸 확장하는 방향으로
제안해 주세요.
```

## 실행

1. 도구 후보를 3개 이상 뽑아요 (읽기 2개 + 쓰기 1개를 권장해요)
2. 계약을 설계해요 — `contract.json`을 만들고, 출력에는 근거 ID 필드를 꼭 넣어요
3. 가상 실행을 해 봐요 — `mock-response.json`을 만들고 계약과 하나씩 대조해요
4. `approval-rule.md`를 작성해요
5. [선택] 개발이 가능한 팀은 최소한으로 동작하는 서버를 만들어 봐요
6. `../mx-agentic-ai-day1-prd/docs/prd.md`의 Canvas 5·6을 갱신해요
7. 도구 계약이 다 준비되면 임시 환경(`mx-agentic-ai-day3-mcp-tools/_sandbox/`)에서 가상 테스트를 해도 되는지 강사에게 먼저 확인해요. 승인을 받으면 아래 [테스트 조건]에 따라 진행해요
8. 가상 테스트 결과가 안정적이면 강사나 멘토에게 최종 승인을 요청해요 (레포의 `approve_handoff.py --day 3`으로 기록해요)

**Day 3 승인 조건**: 도구 계약이 최소 2개(읽기 1 + 쓰기 1) / 모든 mock 응답에 근거 ID가 있을 것 / 승인이 필요한 도구를 표시할 것

## 테스트 조건 (가상 테스트 — 임시 환경)

| 조건 | 내용 |
|---|---|
| 실행 위치 | `mx-agentic-ai-day3-mcp-tools/_sandbox/`에서만 진행해요. `mcp/` 원본 계약 파일은 건드리지 않아요 |
| 데이터 | 합성 데이터로 만든 mock 응답만 사용해요 |
| 테스트 범위 | 읽기 도구 1개와 쓰기 도구 1개를 3~5회 순서대로 호출해서, 승인 토큰 없이는 쓰기 도구가 실행되지 않는지 확인해요 |
| 되돌리기 | `_sandbox/` 폴더만 지우면 원래대로 돌아와요. 실제 서버나 시스템에는 연결하지 않아요 |
| 시간 | 10분 안에 끝내요 |
| 결과 반영 | 문제를 찾으면 승인을 받은 뒤에 `contract.json`을 고쳐요. 가상 테스트 자체는 정식 산출물에 넣지 않아요 |

## 문제 해결

| 상황 | 대응 |
|---|---|
| 도구가 너무 커서 계약이 복잡해져요 | 도구 하나가 책임 하나만 맡도록 쪼개세요 |
| mock 응답에 근거 ID를 못 넣겠어요 | Day 2의 `../mx-agentic-ai-day2-knowledge-harness/knowledge/` 항목과 연결되는지 다시 확인해 보세요 |
| "이게 실제로 되긴 하나" 싶어 불안해요 | Day 3의 목표는 구현이 아니라 계약 검증이라는 점을 다시 짚어 주세요 |
| 읽기인지 쓰기인지 헷갈려요 | "이 도구를 실행하면 되돌릴 수 있나?"로 판단하세요. 되돌릴 수 없으면 쓰기 도구예요 |
| 기존 Node 서버 코드와 부딪혀요 | `mcp/`는 계약과 mock 전용 폴더로 따로 두고, 기존 `src/`는 [선택] 단계에서만 건드리세요 |
